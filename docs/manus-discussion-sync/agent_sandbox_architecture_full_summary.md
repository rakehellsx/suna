# 商业化多租户场景下的 Agent 与沙箱架构分析

**作者：Manus AI**

## 摘要

本文整合前述全部讨论，围绕四个连续问题展开。第一，比较“沙箱里跑 OpenCode”与“OpenCode 调用沙箱 API”两种模式在商业化多租户场景中的合理性，并判断更接近 Manus 外在形态的是哪一种。第二，进一步拆解这两种模式在控制面、执行面、状态管理、权限治理、运维升级和计费模型上的差异。第三，给出一次完整 agent 任务在商业化平台中的调用时序，包括任务创建、沙箱申请、命令执行、状态回收与计费出账。第四，分析在多租户场景下，如何通过分层复用、动态调度与风险控制来优化沙箱复用策略，以降低总体成本。

全文的总判断可以浓缩为一句话：**面向商业化多租 SaaS，通常应采用中心化 agent 编排层加隔离执行沙箱的模式；在复用策略上，则应最大化无状态层复用，最小化高风险有状态层复用。**

## 一、两种架构模式的本质差异

当讨论“沙箱里跑 OpenCode”和“OpenCode 调用沙箱 API”时，实际上讨论的是两种不同的系统分层方式。前者的含义是：把 agent runtime、本地工具适配、任务推进逻辑，甚至部分会话状态，都放进每个租户自己的隔离环境中运行。后者则是：agent 的主要编排、状态管理、权限治理与策略判断运行在平台控制层，当需要执行命令、处理文件、驱动浏览器或访问网络时，再通过统一接口调用租户专属沙箱。

二者看似都能完成“agent 调用沙箱执行任务”的目标，但从平台化程度上看差别很大。前者更像是把每个租户都变成一套相对完整的小型运行实例，后者则更接近典型的 **control plane / execution plane** 分层架构。在商业化多租户产品里，平台化程度往往直接决定了安全治理能力、可观测性、升级效率和成本结构。

| 维度 | 沙箱里跑 OpenCode | OpenCode 调用沙箱 API |
|---|---|---|
| 架构本质 | 编排与执行尽量内聚在租户隔离环境内 | 编排集中在平台，执行下沉到隔离环境 |
| 平台化程度 | 较低，更像每租户独立运行实例 | 较高，更像统一平台 + 独立工作单元 |
| 多租适配性 | 可行，但运维和治理负担重 | 更适合 SaaS、多租与统一运营 |
| 最大优势 | 边界直观，适合私有化或强主权部署 | 成本、调度、治理、升级更优 |
| 最大问题 | 实例重、版本散、监控难、成本高 | 需要设计清晰的执行接口与权限边界 |

## 二、在商业化多租户场景下，哪种更合理

如果把问题限定为**商业化多租户**，更合理的方案通常是 **“OpenCode 调用沙箱 API”**，而不是“把完整 OpenCode 跑在每个租户沙箱里”。原因在于，多租 SaaS 的核心要求并不是“能执行”，而是要同时满足 **隔离、安全、成本、可观测、可恢复、可计费、可升级** 等多重约束。agent 本身包含大量平台属性很强的能力，例如会话状态、任务计划、策略路由、权限控制、重试机制、计费统计和日志审计，这些能力天然更适合集中到平台控制层统一处理。

相对地，沙箱更适合承载那些高风险、强隔离、可副作用的能力，例如 shell 命令执行、文件系统变更、依赖安装、浏览器会话、联网访问和本地进程管理。换言之，**长期状态与平台策略应尽量中心化，不可信执行与副作用操作应尽量沙箱化**。这类分工通常能让 SaaS 平台更容易做资源池化、任务调度、权限治理和成本归因。

| 核心诉求 | 更适合的平台做法 | 原因 |
|---|---|---|
| 多租隔离 | 沙箱执行面隔离，平台集中治理 | 隔离边界清晰且策略统一 |
| 成本优化 | 控制层共享，执行层按需分配 | 降低每租户实例冗余 |
| 升级运维 | 中心控制层统一升级 | 避免沙箱内部版本漂移 |
| 可观测性 | 集中 trace、日志与指标 | 更容易做排障与审计 |
| 产品演进 | 扩展编排能力而非重做镜像 | 迭代速度更快 |

这并不意味着“沙箱里跑 OpenCode”没有价值。它在私有化部署、离线运行、本地 first 自动化、强数据主权或企业内网闭环场景中依然很有意义。只是当目标是一个需要服务大量租户、持续快速迭代、并进行统一运营的商业 SaaS 平台时，后者通常更稳妥。

## 三、从外在特征判断 Manus 更接近哪一种

基于外在行为进行逆向判断，Manus 更像是**中心化 agent 编排层 + 沙箱执行层**，也就是更接近“OpenCode 调用沙箱 API”这一类架构，而不是把完整 agent 主体完全塞进沙箱里长期运行。这个判断不是基于内部实现披露，而是基于外在产品行为的结构特征。

首先，它表现出明显的统一编排感。任务被拆成阶段推进，用户交互、工具调用和结果交付都有统一规范，这通常意味着存在一个高于单个沙箱实例的控制层。其次，它暴露出的执行能力边界更像标准化接口，例如命令执行、文件读写、网页访问、计划管理和结果交付，这些能力更符合“受控执行原语”的产品形态，而不是“在租户环境中本地直连一切”的通用程序。再次，它具备明显的平台治理特征，例如任务阶段控制、交付流程一致性、能力边界稳定性等，这些都说明系统里存在统一的控制面。

| 对 Manus 的外在观察 | 更可能对应的架构 | 原因 |
|---|---|---|
| 统一的任务规划与阶段推进 | 中心化编排层 | 说明存在统一任务控制 |
| 标准化的执行能力边界 | 调用受控执行接口 | 更像沙箱能力被抽象成原语 |
| 稳定的交付与治理规范 | 平台控制面 | 有利于权限、审计与计费 |
| 多能力协同但边界清晰 | 编排层与执行层分离 | 更符合平台型 agent 架构 |

因此，如果问题是“Manus 更像哪种”，比较稳妥的结论就是：**更像平台侧 agent/runtime 负责编排，再把代码执行、文件系统、浏览器和网络等能力下沉到隔离执行环境中。**

## 四、进一步展开：控制面与执行面的系统架构差异

如果继续往系统设计层面下钻，两种模式的根本区别在于：**平台状态应该放在哪里，风险执行应该放在哪里。** 在成熟的多租户平台中，任务对话历史、计划树、重试策略、权限判断、模型路由、计费上下文、审计日志等，通常都被视为平台状态；而工作目录、进程树、临时文件、浏览器会话和本地依赖环境，则更接近执行状态。

如果将这些平台状态也塞进租户沙箱，就需要处理跨任务持久化、状态恢复、镜像升级兼容、实例迁移和异常恢复等大量复杂问题。相反，若平台控制层维护主要状态，沙箱只承担执行上下文，那么任务恢复和平台治理会容易得多。

> **长期状态、产品策略、权限与计费，应尽量留在平台；短期执行、副作用操作与不可信代码，应尽量落在沙箱。**

这条原则不仅适用于逻辑分层，也直接影响权限模型和计费模型。权限问题的本质不是“能不能跑”，而是“谁在什么前提下能调用哪些能力”。如果 agent 主体在沙箱里，权限治理就更像把策略分散下发到大量实例；如果 agent 在平台侧调用沙箱 API，则更容易做成“调用前统一鉴权、调用中策略拦截、调用后审计回放”的三段式治理链路。

| 架构问题 | 沙箱里跑 OpenCode | OpenCode 调用沙箱 API |
|---|---|---|
| 状态管理 | 大量状态分散在沙箱内 | 平台集中保存长期状态 |
| 权限治理 | 需要逐实例生效 | 可统一策略判断与拦截 |
| 计费归因 | 容易混入内部调度开销 | 更自然地拆成控制成本与执行成本 |
| 故障恢复 | 依赖实例内部状态完整性 | 更容易从平台恢复点继续 |
| 运维升级 | 版本漂移风险大 | 平台统一升级，执行镜像标准化 |

## 五、一次完整任务的调用时序

为了更具体地理解这类系统如何运作，可以把一次真实的商用 agent 任务拆成一个完整生命周期。这里假设系统由六类核心组件组成：**API 网关、任务控制器、Agent 编排器、沙箱调度器、沙箱执行面、计费与审计系统**。用户感知到的是一轮连续对话，但系统内部实际上是一条由多个资源对象和状态阶段串联起来的执行链路。

| 组件 | 主要职责 |
|---|---|
| API 网关 | 接收请求、鉴权、限流、路由 |
| 任务控制器 | 创建任务对象，维护生命周期状态 |
| Agent 编排器 | 规划步骤、决定何时申请沙箱与何时结束 |
| 沙箱调度器 | 分配或复用执行环境，选择镜像与规格 |
| 沙箱执行面 | 执行命令、管理文件、浏览器和进程 |
| 计费与审计系统 | 记录消耗、保留审计轨迹、生成出账明细 |

### 5.1 任务创建

用户请求首先抵达 API 网关。网关先做身份验证、并发配额检查、风控判断和请求路由，并生成贯穿全链路的请求 ID。通过前置检查后，请求被转交给任务控制器。任务控制器不会直接执行任务，而是先落库创建任务对象，例如 `task_id`、`workspace_id`、`user_id`、`conversation_id`、`request_payload`、`priority`、`policy_snapshot` 和初始状态 `pending`。这样做的目的是保证任务在任何后续阶段失败，都能被审计、恢复或重试，而不会变成一次只存在于内存中的瞬时调用。

### 5.2 编排预处理与沙箱申请

任务进入编排器后，编排器先做轻逻辑工作，例如读取对话上下文、恢复历史计划、判断是否需要外部执行能力。如果任务只是纯文本回答，则可能不需要沙箱；如果涉及 shell、文件处理、浏览器或网络副作用，则编排器才向沙箱调度器申请执行资源。

这时调度器会判断：是否能复用已有沙箱、是否需要新建实例、应使用何种镜像、是否允许联网、是否需要浏览器、需要多大 CPU 和内存。调度器完成资源准入检查后，返回 `sandbox_id`，并把该实例与任务运行记录绑定。

| 阶段 | 系统动作 | 产出 |
|---|---|---|
| 任务进入编排 | 读取上下文与计划状态 | run context |
| 需求识别 | 判断是否需要沙箱能力 | execution required / not required |
| 资源请求 | 提交规格、镜像、网络、浏览器需求 | sandbox request |
| 调度判断 | 复用或新建，检查配额与准入 | sandbox allocation |
| 初始化绑定 | 关联 `task_id` 与 `sandbox_id` | ready state |

### 5.3 会话初始化与命令执行

沙箱准备好后，系统通常还会做一次会话初始化，例如挂载任务目录、同步用户上传文件、恢复浏览器上下文、注入临时环境变量、创建 shell 会话。任务状态随后从 `pending` 进入 `running`。

命令执行不是把整段任务脚本一次性丢给沙箱，而是由编排器把任务拆成多个受控步骤。每一步都有自己的 `step_id`、超时限制、权限标签和输出通道。执行请求进入执行网关后，网关先做策略检查，再由沙箱内的 executor 创建子进程、绑定标准输出流并回传日志。

| 命令执行链路 | 关键动作 | 关键记录 |
|---|---|---|
| 步骤生成 | 编排器生成可审计 step | `step_id` |
| 策略检查 | 校验命令、路径、网络、超时 | policy decision |
| 提交执行 | 在沙箱内创建子进程 | pid / start_time |
| 流式回传 | 实时返回 stdout、stderr | event stream |
| 收口固化 | 记录退出码、产物路径、资源消耗 | step result |

商用平台通常不会只保留最终退出码，而会保存完整过程事件流。因为实时输出、失败诊断、超时判定、用户界面展示和计费归因都依赖这些中间事件。

### 5.4 状态回收

任务结束后，平台会区分三类状态：长期业务状态、短期恢复状态和敏感临时状态。长期业务状态包括消息记录、任务元数据、计划、最终结果和工件索引，需要持久保存；短期恢复状态包括工作目录缓存、浏览器上下文和运行快照，可按 TTL 暂时保留；敏感临时状态，例如临时密钥、短期令牌和某些中间文件，则应立即销毁。

| 状态类型 | 典型内容 | 回收策略 |
|---|---|---|
| 长期业务状态 | 会话、任务元数据、最终答复、工件引用 | 持久化保存 |
| 短期恢复状态 | 工作目录缓存、浏览器上下文、运行快照 | TTL 保留 |
| 临时敏感状态 | 短期密钥、票据、一次性中间文件 | 立即销毁 |

回收流程通常不是瞬时动作，而是一个收尾链路：先将任务标记为 `succeeded`、`failed` 或 `cancelled`，再把需要长期保留的工件迁移到对象存储，随后通知调度器将沙箱转入 `warm`、`cold snapshot` 或 `terminated` 状态，最后封存审计日志与最后一次运行快照。

### 5.5 计费出账

计费在商用系统中并不是任务结束后才临时计算，而是在整个执行过程中持续生成 usage event。模型网关上报 token 数，沙箱节点上报 CPU 秒、内存峰值和运行时长，浏览器服务上报会话时长，工件服务上报存储与带宽消耗。之后由统一的 rating engine 按套餐和单价规则换算为账单项。

| 计费层次 | 负责内容 | 示例 |
|---|---|---|
| Usage Event | 原始计量 | 120 秒 CPU、4 万 token、1 次沙箱启动 |
| Rating | 单价换算与额度抵扣 | 免费额度、折扣、超额单价 |
| Billing Line Item | 明细账单项 | “沙箱计算 2 分钟”“模型调用 4 万 token” |
| Statement | 用户可见账单 | 日账单、月账单、工作区账单 |

一次成熟的任务生命周期，本质上不是单次命令调用，而是一条**可调度、可恢复、可审计、可计费**的完整链路。

## 六、多租户下如何优化沙箱复用策略以降低成本

在多租户场景中，优化沙箱复用的关键，不是单纯追求更高复用率，而是在**隔离、安全、时延与成本**之间取得平衡。真正有效的策略通常不是“复用一个完整、带状态的旧沙箱”，而是做**分层复用**：镜像层复用、依赖层复用、工作目录缓存复用、同租户会话级 warm sandbox 复用，以及极为谨慎的高风险状态复用。

> **多租户系统里，最优目标不是最大化完整沙箱复用，而是最大化无状态层复用，最小化高风险有状态层复用。**

从成本结构看，沙箱成本主要有三类：启动成本、环境准备成本和空闲占用成本。启动成本来自拉起容器或微虚机；环境准备成本来自重复安装依赖、拉仓库和预热浏览器；空闲占用成本则来自长时间保温实例的资源浪费。因此，复用设计应分别针对这三类成本施策，而不是简单延长所有沙箱的存活时间。

| 成本来源 | 典型表现 | 更优优化方向 |
|---|---|---|
| 启动成本 | 拉起实例慢、初始化网络与 runtime 慢 | warm pool、模板实例、快照恢复 |
| 环境准备成本 | 反复安装依赖、重复下载工具和仓库 | 镜像分层、依赖缓存、对象缓存 |
| 空闲占用成本 | 沙箱闲置但持续吃资源 | 分级保温、预测式 TTL、弹性降配 |

### 6.1 分层复用，而不是整体复用

跨租户最值得复用的是**只读、可校验、不可回写**的基础层资源，例如基础镜像、语言运行时、浏览器二进制和预编译工具链。它们风险低，收益大，应优先跨租户共享。接下来是包管理器缓存、对象缓存和依赖下载结果，这一层也可以跨租户复用，但要采用内容寻址和完整性校验，以避免缓存投毒。再往上才是同租户工作目录缓存、仓库克隆和中间产物；再上一层则是同会话的 warm sandbox 和浏览器登录态。

| 复用层级 | 复用对象 | 推荐边界 | 推荐策略 |
|---|---|---|---|
| L0 | 基础镜像、运行时、浏览器二进制 | 跨租户 | 只读共享 |
| L1 | 包缓存、对象缓存、依赖下载 | 跨租户但需校验 | 内容寻址 + 防投毒 |
| L2 | 工作目录、仓库副本、构建缓存 | 同租户/同工作区 | 隔离卷复用 |
| L3 | warm sandbox、预热 shell | 同租户/同会话 | 短 TTL 保温 |
| L4 | 浏览器 session、登录态 | 同用户/同会话 | 严格主体绑定 |
| L5 | 临时密钥、敏感中间态 | 不复用 | 任务结束即销毁 |

### 6.2 让复用决策变成策略引擎，而不是固定规则

不是所有任务都适合同一种复用策略。只读分析任务、连续调试任务、登录态浏览器任务、高敏感企业任务，它们的复用收益和风险完全不同。因此调度器应为每个任务生成“复用画像”，综合租户、会话、任务类型、风险等级、是否带登录态、是否修改工作目录、资源规格和当前容量压力等信息，来判断是复用已有环境、部分复用、快照恢复还是强制新建。

可以用一个简化的评分思想来描述：

> **复用收益分 = 预估重启成本节省 − 预估空闲占用成本 − 风险惩罚项 − 资源紧张惩罚项**

只有在收益为正时，继续保温或复用才是合理的。

| 任务特征 | 推荐复用策略 |
|---|---|
| 纯只读分析、短任务 | 同租户 warm sandbox |
| 同一仓库连续调试 | 同会话沙箱 + 工作目录缓存 |
| 浏览器登录后续跑 | 仅同用户同会话复用 |
| 高敏企业数据处理 | 强制新建或极短 TTL |
| 依赖安装很重的任务 | 强化镜像层与依赖缓存 |
| 高风险未知命令 | 降低实例级复用 |

### 6.3 采用分级保温，而不是简单保活或销毁

合理的沙箱状态不应只有“运行中”和“已销毁”两种。更好的做法是设立 `hot`、`warm`、`cold snapshot` 和 `terminated` 四级状态。`hot` 几乎完整保留运行现场，适合非常短间隔的连续任务；`warm` 保留工作卷和基础环境，释放部分昂贵资源；`cold snapshot` 仅保留快照和恢复索引；`terminated` 完全销毁实例。这样可以根据用户行为和资源压力动态调整空闲成本。

| 状态 | 保留内容 | 成本 | 恢复速度 | 适用场景 |
|---|---|---|---|---|
| hot | 运行现场、工作目录、部分进程上下文 | 高 | 极快 | 高频连续交互 |
| warm | 工作卷、基础环境、少量上下文 | 中 | 快 | 常规会话续跑 |
| cold snapshot | 快照、缓存索引、工件 | 低 | 中 | 间歇回访 |
| terminated | 无实例，仅保留业务状态 | 最低 | 慢 | 长尾低频任务 |

### 6.4 用预测式 TTL 替代固定 TTL

固定 TTL 通常不是最优解，因为用户行为和任务模式差异很大。连续调试、增量修改和浏览器续跑任务往往值得更长的 warm TTL；一次性批处理和低频分析则应快速回收。更成熟的做法是让 TTL 与用户最近交互间隔、同类任务续跑概率、套餐等级、资源峰谷和风险等级联动。

### 6.5 区分“可复用状态”与“危险状态”

真正好的复用策略不是回答“要不要复用这个沙箱”，而是回答“沙箱里哪些状态可以留下”。只读运行时、内容寻址缓存、工作目录副本往往有较高复用价值；而浏览器 cookie、临时令牌、shell 历史、环境变量和进程上下文则属于危险状态，即便在同租户场景下也应谨慎保留。

| 状态类型 | 复用价值 | 风险等级 | 处理建议 |
|---|---|---|---|
| 只读运行时与工具链 | 高 | 低 | 长期复用 |
| 内容寻址依赖缓存 | 高 | 中 | 校验后复用 |
| 工作目录与仓库副本 | 高 | 中高 | 同租户复用 |
| 浏览器登录态 | 中 | 高 | 同用户同会话短 TTL |
| 环境变量与临时密钥 | 低 | 很高 | 立即清理 |
| shell 历史与进程上下文 | 中 | 高 | 默认清除 |

## 七、工程落地优先级建议

如果从工程投入产出比出发，不建议一开始就追求复杂的跨任务智能路由或全量快照恢复。更合理的落地顺序通常是：先做基础镜像与工具链预热，再做依赖缓存与对象缓存，然后做同租户会话级 warm sandbox，随后增加动态 TTL 和容量感知回收，最后再考虑更复杂的任务指纹路由和高级评分模型。

| 落地阶段 | 优先级 | 原因 |
|---|---|---|
| 镜像与运行时预热 | 最高 | 收益大、风险低、实现清晰 |
| 依赖与对象缓存 | 很高 | 显著减少环境准备成本 |
| 同租户会话级 warm sandbox | 很高 | 兼顾体验、安全与成本 |
| 动态 TTL 与容量感知回收 | 中高 | 控制空闲占用 |
| 快照恢复与相似任务路由 | 中 | 收益可观但复杂度高 |
| 更激进的有状态复用 | 较低 | 治理与安全代价高 |

## 八、总结合并结论

将前述讨论合并起来，可以形成一个比较稳定的总体判断。对于商业化多租户平台，最合理的形态通常不是把完整 agent 主体放到每个租户沙箱里运行，而是构建一个**中心化编排层 + 隔离执行层**。这种结构能更好地处理平台状态、权限策略、审计追踪、资源池化和计费归因。Manus 从外在特征看，也更像这一类产品。

在任务运行层面，一次完整任务应被设计为从请求接入、任务创建、资源调度、步骤执行、状态回收到计费出账的完整生命周期，而不是一次孤立的命令调用。在资源优化层面，沙箱复用不应以复用完整实例为目标，而应围绕分层复用、动态评分、分级保温和危险状态清理来设计。最关键的原则有两条：

> **面向产品化与多租 SaaS，agent 应尽量中心化，风险执行应尽量沙箱化。**

> **跨租户复用只读层，同租户复用工作层，同会话复用热状态，敏感状态永不复用。**

如果把这两条原则同时落实，通常就能在隔离、安全、成本、时延与运维效率之间取得较好的工程平衡。
